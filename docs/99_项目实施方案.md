# 软件工程大作业·项目实施方案与架构基线

> 项目代号：筑测云（ZhuceCloud）
> 选题：土木工程检测数据管理平台
> 版本：v0.1（架构基线，后续以详细设计文档为准）
> 日期：2026-11-06

## 1. 选题与建设目标

面向中小检测机构与施工项目部，建设一个 Demo 级 B/S 系统，完成"工程项目—检测样品—检测记录—结果判定—数据看板"的闭环，并把开发过程中 AI Agent 的分级协作、失效评分与可靠性监管沉淀为系统内置模块，使作业第 11、12 条要求具备可运行载体而非纯文档描述。

系统边界：

- 包含：登录鉴权、用户与角色管理、工程项目管理、样品登记、检测记录录入与自动判定、统计看板、AI 任务台账、缺陷台账、Agent 失效率与可靠性统计。
- 不包含：真实检测设备对接、报告签章、第三方支付、多租户计费。上述内容在可行性分析中作为范围外事项说明。

## 2. 技术栈

| 层次 | 选型 | 说明 |
|---|---|---|
| 前端 | Vue 3 + Vite + Element Plus + ECharts + Axios | 单页应用，构建产物由后端托管，一条命令可运行 |
| 后端 | Python 3.12 + FastAPI + Pydantic v2 | RESTful API，统一响应与异常处理 |
| 数据访问 | SQLAlchemy 2.0 + Alembic | ORM + 版本化迁移 |

| 鉴权 | JWT + RBAC | 三角色：管理员 / 检测工程师 / 查阅人员 |
| 测试 | pytest + httpx + pytest-cov；Edge + playwright-core | 单元/接口测试 + 真浏览器端到端验证 |
| 图表 | Matplotlib（300 dpi PNG + SVG） | 雷达图、用例图、架构图、类图、流程图、帕累托图 |

## 3. 总体架构

采用前后端分离的分层架构：

```
浏览器（Vue3 SPA）
   │  HTTPS / JSON（JWT）
FastAPI 接口层（统一响应、鉴权、RBAC、异常处理）
   │
业务服务层（认证、项目、样品、检测、看板、AI 协作监管）
   │  SQLAlchemy 2.0
SQLite（Alembic 管理表结构）
```

前端构建产物输出到 `backend/app/static`，由 FastAPI 直接托管，实现单进程演示部署；开发期通过 Vite 代理访问 `/api`。

### 3.1 后端模块（自动发现）

| 模块 | 职责 | 主要接口前缀 |
|---|---|---|
| auth | 登录、当前用户、JWT 签发 | `/api/auth` |
| users | 用户与角色管理（管理员） | `/api/users` |
| projects | 工程项目 CRUD、状态流转 | `/api/projects` |
| samples | 检测样品登记与查询 | `/api/samples` |
| tests | 检测记录、自动判定、查询 | `/api/test-records` |
| dashboard | KPI、分布、趋势、合格率 | `/api/dashboard` |
| ai_ops | AI 任务台账、缺陷台账、失效评分、可靠性、分级机制 | `/api/ai` |

模块通过 `pkgutil` 自动发现 `app/modules/*/router.py` 并注册，新增模块无需修改入口文件。

### 3.2 前端页面

## 4. 数据模型（基线）

| 实体 | 关键字段 | 关系 |
|---|---|---|
| users | username、password_hash、display_name、role、is_active | 1:N 检测记录 |
| projects | code、name、client、location、status、start_date、end_date、manager | 1:N 样品 |
| samples | code、project_id、type、spec、produced_on、quantity、status | N:1 项目；1:N 检测记录 |
| test_records | sample_id、item、standard_value、measured_value、unit、rule、conclusion、tested_by、tested_at | N:1 样品/用户 |
| ai_tasks | phase、task_name、level、agent_name、status、五维评分、failure_score、human_minutes、retries | 独立台账 |
| defects | title、phase、category、severity、occurrences、ai_related、status | 独立台账 |

枚举：角色（ADMIN/ENGINEER/VIEWER）、项目状态（PLANNING/IN_PROGRESS/ACCEPTED/ARCHIVED）、样品类型（CONCRETE/STEEL/SOIL/MORTAR/ASPHALT）、检测结论（PASS/FAIL）、AI 等级（L1/L2/L3）、任务状态（SUCCESS/PARTIAL/FAILED）。

## 5. Agent 失效评分基线

五维评分（0–5 分，越高失效越严重）：

| 维度 | 权重 | 观察点 |
|---|---|---|
| 正确性 C | 25% | 事实、公式、字段、业务规则是否正确 |
| 完整性 I | 20% | 需求点、异常分支、文档要素是否齐全 |
| 可运行性 R | 25% | 产物能否直接运行，测试是否通过 |
| 可维护性 M | 15% | 结构、命名、注释、可修改性 |
| 合规与安全 S | 15% | 权限、密钥、数据合规、许可证 |

失效分 FS = 20 × (25C + 20I + 25R + 15M + 15S) / 100，取值 0–100，越高越不可靠。

| 区间 | 等级 | 处置 |
|---|---|---|
| 0–19 | 低失效 | 抽检后可采信，保持 L1 |
| 20–39 | 中失效 | 人工复核修正，按 L2 管理 |
| 40–59 | 高失效 | 人工重做，等级上调一级 |
| 60–100 | 严重失效 | 阻断交付，L3 接管并做根因分析 |

阶段综合可靠性 R = 0.6 × (100 − 平均失效分) + 0.4 × 一次通过率 × 100。该公式在后端 `/api/ai/stats`、前端图表与维护文档中三处保持一致。

## 6. AI 分级原则

- **L1（Agent 自动完成）**：边界清晰、可自动验收的工程化任务，如脚手架、CRUD 模板、图表数据聚合、格式化文档；自动门禁（编译/测试/模式校验）通过即可采信。
- **L2（人机协作）**：存在业务歧义或体验取舍的任务，如需求澄清、判定规则、交互设计、测试用例设计；Agent 产出草稿，人负责确认与修改。
- **L3（纯人工）**：高风险或强合规任务，如评分口径、权限模型最终确认、验收结论、敏感数据处理、最终交付评审；Agent 仅可提供辅助信息，不直接产出交付物。

升级规则：FS ≥ 40 上调一级；连续 2 次失败或 FS ≥ 60 直接转 L3 并由人接管；降级需连续 3 个同类任务 FS < 20 且有测试证据。
